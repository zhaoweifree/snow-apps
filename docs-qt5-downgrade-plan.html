Qt 5.15 / Qt 6.12 双版本兼容

Qt6 降级 Qt5 实施方案（Windows 优先验证）

决策：维持 Qt5 路线；保留 Windows 分支，先在 Windows 用 Qt5 编译冒烟测试，通过后再上 UOS。 策略：不删除 Qt6 支持，把工程改造成「一套源码，Qt 5.15 / Qt 6.12 双版本皆可编译」。 基线：SNOW_SHOT_VERSION = 1.2.8（根 CMakeLists.txt:18）｜当前 Qt 契约：6.12.0（scripts/qt-toolchain.json） 文档定位：与 docs-uos-linux-port.md（Linux 移植总方案）、docs-windows-arm64-build.md 同级

0. 方案形态：为什么是「双版本」而不是「纯 Qt5」

这是本方案与前一版最大的区别，也是它成立的前提。

Qt 公司官方自 Qt 5.15 起引入了 versionless 目标与命令，并且 Qt 6 同样提供：

每个被加载的 Qt 模块都会定义库目标，名称以 Qt6:: 开头……这些目标也可使用 Qt:: 前缀：Qt::Core、Qt::Gui 等。 —— Qt 6 官方文档 Imported targets

Qt 5.15 引入了 versionless targets……可以同时引用 Qt6::Core 或 Qt::Core。独立于使用 Qt 6 还是 Qt 5，都可以使用导入的 Qt::Core 目标。 —— Qt 官方文档 Qt 5 and Qt 6 compatibility

结论：Qt6::X → Qt::X 是一次官方背书、双向生效的重命名。 于是改造可以做成一棵分支树而非重写：

纯 Qt5 重写（前一版方案） 双版本改造（本方案）
现有 Qt6 构建 失效，不可回归 保持可用，作为对照基线
定位「降级引入的 bug」 无法区分 可二分对比
回滚成本 高（跨 112 文件） 低（每次一个 commit）
迁移期工作量 一次性大 增量、可中断
UOS 目标 达成 达成

落地含义：同一份源码在 SNOW_QT_MAJOR=6 与 =5 下都能配置、编译、运行。所有版本差异被收敛到 3 个新增文件 + 1 个 CMake 模块里，不进业务代码。

1.3 三个容易误判的点（已逐条核实，避免做无用功）

  1. QImage::sizeInBytes() 不用改。 经查 Qt 5.15 文档，该方法存在，只是返回 int（Qt6 返回 qsizetype）。 135 处调用在 Qt5 下可编译；风险仅在超大位图（>2GB）时的溢出，而截图工具不会触及。 → 处理：保留，仅在 code review 时留意 qint64 累加场景。
  2. Qt::SkipEmptyParts 不用改。 它是 Qt 5.14 引入的（QString::SkipEmptyParts 的替代名）。5 处调用在 5.15 下合法。
  3. QAction / QShortcut 不用改。 虽然 Qt6 把它们从 QtWidgets 移到了 QtGui，但 Qt5 里它们本就在 QtWidgets， #include <QAction> 两种版本都能解析。

反过来，QKeyCombination 是必须处理的硬点：它自 Qt 6.0 引入，Qt5 中无等价类——Qt5 时代的写法是把 Qt::Key 与 Qt::KeyboardModifiers 按位或成 int 直接传。QKeyCombination::fromCombined()/toCombined() 这对 API 的存在本身就证明了这一点。

第 13 条最隐蔽：不是简单地换个类型别名就完事。Qt5 的 qHash 兜底模板长这样：

template<typename T> inline uint qHash(const T &t, uint seed)
    noexcept(noexcept(qHash(t)))
{ return qHash(t) ^ seed; }          // QtCore/qhashfunctions.h:117

它通过单参 qHash(t) 二次派发，因此用户自定义重载在 Qt5 侧必须写成 SnowHashSeed qHash(const Key& key, SnowHashSeed seed = 0)——默认值是必需的， 否则 Qt5 找不到单参可调用版本（Qt6 直接调 qHash(key, seed)，不需要）。加默认值对 Qt6 无害。

1.5 两个改变计划的实测结论（本轮新增）

(1) Qt 5.15 自带 QRhi —— viewer 渲染后端不必重写

C:/Qt/5.15.2/msvc2019_64/include/QtGui/5.15.2/QtGui/private/ 下实际存在：

仍需处理的两处真差异：

  1. include 路径：Qt6 的公开头是 <rhi/qrhi.h> / <rhi/qrhi_platform.h> / <rhi/qshader.h>； Qt5 只有私有头 <QtGui/private/qrhi_p.h> / <QtGui/private/qshader_p.h>，且各后端 （QRhiVulkanInitParams 等）要按需包含 <QtGui/private/qrhivulkan_p.h> 之流。
  2. Qt5 无 HDR：qrhi_p.h 里 Hdr/HDR grep 为 0，因此工程里 QRhiSwapChain::HDRExtendedSrgbLinear、swapChain_->hdrInfo()、QRhiSwapChainHdrInfo、 luminanceBehavior、limitsType 全部不存在（rhi_image_window.cpp 中 3 组、约 10 行）。 Qt5 侧必须显式降级为 SDR 分支，并在代码里标注这是有损降级。

代价与风险：私有 API 在不同 5.15.x 补丁间无语义保证；UOS 上需要 qtbase5-private-dev 才能拿到 qrhivulkan_p.h 等头文件（部署前置条件，需在 UOS 侧确认）。 若该包在 UOS 上不可得，才回退到原「重写为 QOpenGLWidget」方案。

(2) QSB 版本不兼容 —— 这是走 QRhi 路线的真正硬卡点

.qsb 是预编译并入库的（snow_image_viewer/resources/shaders/*.qsb， 由 snow_image_viewer/scripts/compile-shaders.ps1 调 Qt6 的 qsb.exe 生成， scripts/test-qt-shader-contract.ps1 强制其版本匹配 scripts/qt-toolchain.json 的 6.12.0）。 运行时经 :/shaders/*.qsb 从 qrc 读取，交给 QShader::fromSerialized()。

实测两条硬事实：

Qt 6.12（现状） Qt 5.15.2（目标）
QShaderPrivate::QSB_VERSION 9 5（白名单 1–5）
版本不符时 — qWarning("Attempted to deserialize QShader with unknown version %d.") 后返回空 QShader
套件自带烘焙工具 qsb.exe（契约要求存在） 无 qsb.exe（C:/Qt/5.15.2/msvc2019_64/bin/ 下不存在）

即：现有 .qsb（v9）在 Qt5 下会被静默丢弃成空 shader（表现为黑屏/渲染异常）， 必须在 Qt5 路线下重新烘焙成 ≤ v5。而 Qt6 的 qsb 只提供 --qsbversion 64|65（Qt 6.4 / 6.5）这类回退档，没有 v5 档，所以需要 Qt 5.15 自身的 Shader Tools（qtshadertools，5.15 分支）来出包。

顺带澄清一个容易误判的格式问题：.qsb 文件开头不是 QSB 魔数，而是 4 字节大端原始长度 + zlib 流（实测 00 00 11 A0 78 9C ...，解压后正好 4512 字节）。 这不是坏文件——Qt 的 QShader 序列化本身就是 qCompress 封装， Qt5/Qt6 两侧一致，不需要手工解包。

namespace snow::compat {
class QKeyCombination
{
public:
    constexpr QKeyCombination(Qt::KeyboardModifiers mods, Qt::Key key) noexcept
        : m_key(key), m_modifiers(mods) {}
    constexpr explicit QKeyCombination(Qt::Key key = Qt::Key_unknown) noexcept
        : m_key(key), m_modifiers(Qt::NoModifier) {}
    [[nodiscard]] constexpr Qt::Key key() const noexcept { return m_key; }
    [[nodiscard]] constexpr Qt::KeyboardModifiers keyboardModifiers() const noexcept { return m_modifiers; }
    [[nodiscard]] constexpr int toCombined() const noexcept
    {
        return static_cast<int>(m_key) | static_cast<int>(m_modifiers);
    }
    [[nodiscard]] constexpr bool operator==(const QKeyCombination&) const noexcept = default;
private:

    Qt::KeyboardModifiers m_modifiers;
};

// ── 3. QList::removeIf（Qt 6.1 引入） ─────────────────────
namespace snow::compat {
template <typename Container, typename Predicate>
qsizetype removeIf(Container& container, Predicate predicate)
{
#if QT_VERSION >= QT_VERSION_CHECK(6, 1, 0)
    return container.removeIf(predicate);
#else
    qsizetype removed = 0;
    for (auto it = container.begin(); it != container.end();) {
        if (predicate(*it)) { it = container.erase(it); ++removed; }
        else { ++it; }
    }
    return removed;
#endif
}

(1) 第 5 条的坑中坑：Qt5 的 lrelease 不会因为未完成而失败，统计行也看不出来

同一份 .ts（1 条已完成 + 1 条 type="unfinished"）在 Qt 5.15.2 下的原始输出：

Updating 'mix.qm'...
    Generated 1 translation(s) (1 finished and 0 unfinished)
    Ignored 1 untranslated source text(s)
$ echo $?
0

(X finished and Y unfinished) 里的 Y 描述的是已生成条目的完成度，未完成条目 被归到另一行；加不加 -nounfinished 都不改变这两行，退出码恒为 0。 所以"照抄统计行做门禁"会得到一条永远通过的假门禁——比构建失败危险得多 （残缺目录会照常进安装包）。SnowQt5LreleaseEnforce.cmake 因此用两个独立信号：

  1. 主判据：源 .ts 里是否存在 type="unfinished"（与 AGENTS.md 的措辞逐字对应， 不依赖任何工具的文案）；
  2. 交叉校验：lrelease 是否报了 Ignored N untranslated source text(s)（N > 0）。

实测两者在同一条件下触发（都只针对 type="unfinished"）；一个空但没有 type="unfinished" 的 <translation></translation> 两个信号都不报——这与 Qt6 行为一致， 故不额外收紧。

(4) 编译过了、链接不过：opencv4 的 CRT 与共享 Qt5 套件冲突

第 (3) 节全部修完后，engine 档 C++ 全部编译通过，失败前移到链接：

opencv_imgproc4d.lib(morph.dispatch.cpp.obj) : error LNK2038:
  检测到 RuntimeLibrary 的不匹配项: 值(MTd_StaticDebug)不匹配值(MDd_DynamicDebug)

根因在端口而不是代码：cmake/vcpkg-overlay-ports/opencv4/portfile.cmake:9 无条件 set(VCPKG_CRT_LINKAGE static)，因为发布配置链接的是静态 Qt 套件 + 静态 CRT， std::string / std::vector 跨 CRT 堆传递会直接崩。而 Qt5 验证路线用的是共享 Qt 5.15.2 套件（msvc2019_64，/MDd），/MT 的 OpenCV 根本进不了它的链接行—— 这是 LNK2038，不是可以忽略的警告。

处置：默认保持静态 CRT 不变，另开一个只给 Qt5 验证路线用的变体端口： .workbuddy/qt5-port/vcpkg-mirror/overlay-ports/opencv4/，它只有两行——set(SNOW_OPENCV_DYNAMIC_CRT TRUE) 然后 include() 仓库里的同一份 portfile。仓库 portfile 里那行改成 if(NOT SNOW_OPENCV_DYNAMIC_CRT)。

为什么不是环境变量（第一版就是环境变量，白跑了一次 49 分钟）：vcpkg 求值 portfile 时用的是 被清洗过的环境，$ENV{SNOW_OPENCV_DYNAMIC_CRT} 恒为空——实测导出 =1 后重装， BUILD_WITH_STATIC_CRT 仍是 1、CMAKE_CXX_FLAGS_DEBUG 仍是 /MTd。CMake 变量在同一次 include() 里可见，所以包装端口是唯一既能生效、又不必改 triplet 的办法（改 triplet 文件会改变 所有端口的 ABI 哈希，等于全量重建）。

镜像 overlay 目录本来就排在仓库目录之前（crashpad 已经在这么用），所以同名端口会后者被前者 覆盖，且 ABI 因 portfile 文本变化而必然重建——这正是需要的。

必须记住的副作用：OpenCV 在同一个 vcpkg_installed 里只能有一个变体。跑完 Qt5 验证、要回到 静态 CRT 的发布配置时，把该目录移除（或排到仓库目录之后）重装一次 opencv4 即恢复 /MT。 这不是"两者共存"的开关。

(5) 换了包装端口还是 /MT：vcpkg 工具链的 CRT 缓存项不做 FORCE

包装端口被 vcpkg 采纳（日志里能看到 installing overlay port from here）、BUILD_WITH_STATIC_CRT 也确实变成 0 了，但编译命令行仍然是 /MTd：

BUILD_WITH_STATIC_CRT:BOOL=0                             ← portfile 的改动生效了
CMAKE_CXX_FLAGS_DEBUG:STRING='/MTd /Z7 /Ob0 /Od /RTC1'   ← 可是标志没变
CMAKE_MSVC_RUNTIME_LIBRARY:STRING=MultiThreaded$<$<CONFIG:Debug>:Debug>$<$<STREQUAL:static,dynamic>:DLL>

第二行里那个 $<STREQUAL:static,dynamic> 是证据：它是 .tools/vcpkg/scripts/toolchains/windows.cmake:3 用上一次的 VCPKG_CRT_LINKAGE（即 static） 展开出来的。该文件里 CMAKE_MSVC_RUNTIME_LIBRARY 与 CMAKE_C/CXX_FLAGS_{DEBUG,RELEASE} 全都是 set(... CACHE STRING "") —— 没有 FORCE。于是同一个 buildtrees/opencv4/x64-windows-{dbg,rel} 目录只要先按静态 CRT 配过一次，旧值就一直存活， 后续配置既不改写也不报错。构建是成功完成的，问题只在链接期以 LNK2038 出现。

这是一类值得单独记住的坑："portfile 已经生效"不等于"编译选项已经生效"，判据必须取 命令行的实际标志（或 dumpbin //directives），不能取 portfile 传给 CMake 的 -D 值。

处置（不删构建目录）：在 portfile 里对动态 CRT 路线显式覆盖这些缓存项。命令行 -D 的优先级高于 set(... CACHE ...)，所以能盖掉陈旧值；而这段被 if(SNOW_OPENCV_DYNAMIC_CRT) 包住， 静态 CRT 的发布配置仍完全走 vcpkg 默认值。

第二版写法又踩了一个坑：把 CMAKE_MSVC_RUNTIME_LIBRARY 覆盖成和 vcpkg 一样的生成器表达式 MultiThreaded$<$<CONFIG:Debug>:Debug>DLL，configure 直接失败——

ninja: error: build.ninja:5: bad $-escape (literal $ must be written as $$)

经 -D 传进去的生成器表达式在这个位置不会被求值，原样落进 build.ninja 的规则变量里。 最终写法是置空（= 不要自动加 /M 标志），CRT 由四条显式的 *_FLAGS_* 决定：

if(SNOW_OPENCV_DYNAMIC_CRT)
  list(APPEND ADDITIONAL_BUILD_FLAGS
      "-DCMAKE_MSVC_RUNTIME_LIBRARY="
      "-DCMAKE_C_FLAGS_DEBUG=/MDd /Z7 /Ob0 /Od /RTC1"
      "-DCMAKE_CXX_FLAGS_DEBUG=/MDd /Z7 /Ob0 /Od /RTC1"
      "-DCMAKE_C_FLAGS_RELEASE=/MD /O2 /Oi /Gy /DNDEBUG /Z7"
      "-DCMAKE_CXX_FLAGS_RELEASE=/MD /O2 /Oi /Gy /DNDEBUG /Z7")
endif()

这套组合先用一个最小工程验过（.workbuddy/qt5-port/tmp-crt-probe/：同一条 vcpkg 工具链 + 同一条 overlay triplet + 一个 main.cpp），dumpbin //directives 给出 /DEFAULTLIB:MSVCRTD（动态调试 CRT），且不再有任何 RuntimeLibrary= 的 FAILIFMISMATCH。

副作用要记住：CMAKE_MSVC_RUNTIME_LIBRARY 置空后，目标不再发 /FAILIFMISMATCH:RuntimeLibrary 指令，也就是说这类库的 MT/MD 混用不会在链接期被 LNK2038 抓到。所以"链接通过"对这条路线来说 不再是 CRT 一致性的证明，判据只能是 dumpbin //directives 看实际 /DEFAULTLIB。

3.8 本轮新增：full 档链接闭环 + 首次真机启动（R37）

结论先说：windows-qt5-full 全量 550/550 目标、EXIT=0、产出 154 MB 的 build/windows-qt5-full/snow_shot/snow_shot.exe；真机启动不再崩溃，日志里 application.ready + capture.backend_ready 都出现，emergency 日志为空。 剩下的是 §3.4 的手测项。

(1) 链接期的两个未定义符号 —— 都是 qt_add_resources 垫片的语义错位

LNK2019: qInitResources_snow_shot_about_assets 与 qInitResources_snow_shot_microtex。 看起来像"资源没编进去"，实际是垫片两处独立的错：

  • 形式 B（qt_add_resources(<VAR> <file.qrc>)）的结果没有回传。垫片内部调 qt5_add_resources，而后者用 set(... PARENT_SCOPE) 回传——它的 parent 是垫片自己， 不是真正的调用方。于是 _resource_sources 在 MicroTeX.cmake 里恒为空，rcc 一次都没跑。 修法：垫片里显式 set(${_snow_var} ... PARENT_SCOPE)。
  • 形式 A 的 qrc 文件名决定了 rcc 的 --name。Qt5 的 qt5_add_resources 用 get_filename_component(outfilename NAME_WE) 当 --name，而 Q_INIT_RESOURCE(x) 展开成 qInitResources_x。早先命名 ${target}_${name}.qrc，于是符号成了 qInitResources_<target>_<name>，与代码要的对不上。修法：qrc 就叫 <资源名>.qrc （实仓 6 处目标形式的资源名全局唯一，不撞名）；同时把 file(GENERATE) 换成 file(CONFIGURE)——qt5_add_resources 在配置期解析 qrc 算 DEPENDS，文件那时还不存在 就等于没有依赖，改 .svg 不会重新 rcc。

(3) 诊断层的真缺陷：qFatal 的正文被丢了

diagnostics.cpp 的 messageHandler 对 QtFatalMsg 是"记事件名 + 立刻 panic"， 正文一个字节都不留，于是崩溃现场只剩 event=qt.fatal 四个字。这不是 Qt5 的问题， Qt6 同一份代码同样会丢，只是之前没人在这个路径上崩过。

修法：panic 之前把正文写进 emergency 通道。三个细节都不是随意选的：

  • 走 snow_diag_emergency（FILE_FLAG_WRITE_THROUGH 同步写）而不是常规异步队列， 因为紧接着 DumpAndCrash 会终止进程，排队的记录多半丢；
  • level 写 FATAL 但不能把 QtFatalMsg 传给 record()——record() 对 Fatal 的处理是 再次 panic，会自递归；
  • 用 QJsonDocument 序列化而不是手拼字符串，正文里的引号/换行/反斜杠不会弄坏日志行。

(4) 移植引入的真缺陷：removeIf 把 end() 缓存在循环外

修完上面两项后的崩溃点，靠转储解出的调用链是：

ConfigurationStore::load → materializeConfiguration → ConfigurationSchema::normalize
  → normalizeToolbarLayout → snow::compat::removeIf<QVector<QStringList>, λ>
  → QVector<QStringList>::erase → qFatal
    ASSERT failure in QVector::erase: "The specified iterator argument 'aend' is invalid"

qt_compat.h 里 Qt5 分支写的是：

const auto end = container.end();   // 快照
while (it != end) { ... it = container.erase(it); ... }

erase 让容器变短，快照立刻变成"当前 end 的下一格"；当 it 走到新的 end() 时 it != 旧end 仍成立，于是解引用一过尾位置并 erase(it)——erase(iterator) 展开成 erase(it, it + 1)，那个 it + 1 就是非法 aend。Qt6 分支走容器自带的 removeIf， 完全不经过这段，所以这是移植引入的。

修法：每轮重新取 container.end()。验证入口：

bash .workbuddy/qt5-port/run-removeif-probe.sh   # 期望 PASS

探针不真的崩，而是镜像 Qt5 的 isValidIterator 判据主动检测"是否即将以非法 aend 调 erase"。原因是实测出来的环境限制：这台机器上进程一崩就拉起 Windows 错误报告 （WerFault → reg.exe），reg.exe 在安全中心黑名单上，命中后整棵进程树被 SIGTERM， 外层脚本连输出都拿不到——第一版探针就是这样"什么都没打印就退出"，很容易误判成探针没跑。

(5) 没有 cdb / WinDbg 时怎么读转储

本机没有 Debugging Tools，dumpbin 也不是符号化工具。补了两个脚本（都在 .workbuddy/qt5-port/）：

  • read-minidump.py：只取异常码、异常地址、模块表。够回答"是访问违例还是 fail-fast、 崩在哪个模块的哪个偏移"。本轮靠它认出了 0xE0534E4F 这个自定义码（'SNO'）， 从而定位到 snow_diag_panic 这条 Rust/C++ 共用的崩溃桥。
  • stack-from-minidump.py：读 MINIDUMP_THREAD.Stack 的栈内存，线性扫描落在 exe .text 内的返回地址，再用 dbghelp.dll（系统组件，不需要装调试器）翻符号。

两个坑值得记下来：

  • SymFromAddr 在本机（MSVC 14.44 的 766 MB PDB + 系统自带 dbghelp）恒返回失败且 GetLastError 为 0，但 SymEnumSymbols 能完整枚举 54 万个符号。所以脚本退一步： 枚举全量符号 → 自己二分查找。SymLoadModuleEx/SymEnumSymbols 的 argtypes 必须显式声明， 否则 ctypes 按 32 位 int 传参，64 位地址被截断，表现同样是"一个符号都翻不出来"。
  • 符号表里混着 vftable / RTTI 描述符等数据符号，最近符号查询会给出 kRecordLimit+0x410 这种一眼假的结果。必须先解析 PE 拿 .text 的虚拟范围做过滤。

3.9 本轮新增：拖框即崩的根因是 Qt 5.15.2 自己的 tryStart(std::function)（R38）

这是 P5 出口前最后一个阻塞缺陷，现已修复并端到端验证。结论放在最前面：

Qt 5.15.2 的 QThreadPool::tryStart(std::function<void()>) 忘了给 QRunnable::ref 做 +1。 而池线程在跑任务前断言 !del || r->ref == 1，且 5.15 里 autoDelete() 就是 ref != -1。 于是「池子收下了、但 ref 仍是 0」必然触发断言。 修法是绕开那条重载，改走一直正确的 tryStart(QRunnable*)。

(1) 现象与第一层定位

拖框松开后 30 ms 内进程消失，emergency 日志给出：

{"event":"qt.fatal.message","level":"FATAL",
 "message":"ASSERT: \"!del || r->ref == 1\" in file thread\\qthreadpool.cpp, line 92",
 "thread":"Thread (pooled)"}

R37 加在 Fatal 记录里的 thread 字段这次没能缩小范围，原因值得记下来： QThreadPoolPrivate::startThread() 对每个池线程无条件执行 thread->setObjectName("Thread (pooled)")，所以给 QThreadPool 对象命名不会传到线程上， 线程名对所有池都一样。顺着这条线只会白跑。

换思路：用串行闸门做二分。在 snow_canvas_image.cpp 的 processChunks() 里加 SNOW_QT5_SERIAL_CHUNKS=1 让分块工作走串行分支，同一条复现路径立刻不再崩。 再在 tryStart 前后打点，最后一条日志是：

[pooltrace] chunks=23 pixels=361201 workers=4 serial=0
[pooltrace] pool before active=0 max=8
[pooltrace] tryStart #1 accepted=1
                    <- 下一行就是 FATAL

pixels=361201 正好是 601×601 的选区，说明这是选区确认时把选区图像做格式转换那条路径， 而崩在新起的第一个池线程上。

(2) 用最小探针把「本项目用法」与「Qt 套件缺陷」分开

本机没有调试器，池线程的调用栈里也只有 QThreadPoolThread::run()（断言在 run() 之前， 拿不到提交方），所以改用纯净探针：.workbuddy/qt5-port/qthreadpool-probe.cpp， 只依赖 cl + Qt5 头/库（无 moc；必须 /MDd + Qt5Cored.lib，否则链接到 release 的 Qt5Core， Q_ASSERT 根本不存在，探针等于什么都没验）。四种模式，同一台机器、同一个 Qt 5.15.2：

模式 调用 结果
start pool->start(std::function) ×3 正常，3 个任务都跑完
trystart-runnable tryStart(QRunnable::create(...)) ×3 正常，3 个任务都跑完
worker / main tryStart(std::function) ×3 + QSemaphore 等待 挂死：accepted=1/1/1，任务一个都不跑
worker-runnable 工作线程里 tryStart(QRunnable::create(...)) ×3 正常

qVersion() 打印确认运行时就是 5.15.2。对照 qtbase 源码可以看清差别：

// v5.15.2 —— 没有 ++ref
QRunnable *runnable = QRunnable::create(std::move(functionToRun));
if (d->tryStart(runnable)) return true;
delete runnable;
return false;

// 5.15 分支 head（补上了，同时补了失败路径的 --ref）
QRunnable *runnable = QRunnable::create(std::move(functionToRun));
Q_ASSERT(runnable->ref == 0);
++runnable->ref;
if (d->tryStart(runnable)) return true;
--runnable->ref; Q_ASSERT(runnable->ref == 0); delete runnable; return false;

而 start(std::function) 是转调 start(QRunnable*) 的，那条重载一直有 Q_ASSERT(ref == 0); ++ref;，所以只有 tryStart(std::function) 这一条重载不可用。 本仓正好只有一处用到它（snow_canvas_image.cpp 的并行分块）。

顺带解释两种症状为什么不一样：应用里断言先炸（ref=0 被池线程抓到）， 探针里表现为「任务永不执行」—— 同一处 ref 记账缺失，在不同线程时序下的两种表现。

(3) 修法与验证

QRunnable* const job = QRunnable::create([&] { consume(); finished.release(); });
if (pool->tryStart(job)) {
    ++started;
} else {
