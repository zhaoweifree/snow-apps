SnipPin 移植到统信 UOS 实施方案

目标平台：统信 UOS（Deepin 系，Debian 衍生），arm64 + amd64 双架构 硬约束：必须兼容 Qt 5 及以下 决策已定（见 §0.4）：维持 Qt5 路线，但改造形态改为「一套源码，Qt 5.15 / Qt 6.12 双版本皆可编译」， 并保留 Windows 分支用于本地验证；具体执行见 docs-qt5-downgrade-plan.md 基线版本：SNOW_SHOT_VERSION = 1.2.8（根 CMakeLists.txt:18） 文档定位：与 docs-macos-build.md、docs-windows-arm64-build.md 同级的移植设计文档

0. 结论摘要与可行性判定

0.1 一句话结论

工程具备清晰的三平台抽象骨架（Windows / macOS 两条腿已实现），但 Linux 支线几乎为零； 真正的移植难点不在 Linux，而在于硬性 Qt6 → Qt5 降级——现有代码不是"停留在 Qt5 老 API"， 而是全面拥抱 Qt 6 专有 API，且 snow_image_viewer 直接依赖 Qt 6 才公开的 RHI 渲染抽象。

0.3 必须向决策方澄清的前置问题

  1. Qt5 的下限版本：建议锁定 Qt 5.15 LTS。UOS 20 出厂为 Qt 5.11，deepin-shared-libs 另提供 Qt 5.15.10 GLES 供 UOS v20 amd64/aarch64 使用；Deepin 23 基线为 Qt 5.15 + 6.x。 若被迫降至 5.12/5.11，QStringDecoder / QLatin1StringView / QByteArrayView / qsizetype / QColorSpace / QImageReader::allocationLimit 等将再增一大层替换工作。
  2. snow_image_viewer 是否在移植范围内：它是唯一使用 QRhi 的模块，Qt5 下无公开等价 API。 建议 Linux 首版不交付查看器，或将其渲染后端重写为 QOpenGLWidget。
  3. ~~Qt5 约束的来源~~ → 已定，见 §0.4。

0.4 决策记录（已确认）

决策 1：维持 Qt5 路线。 不做 AppImage + Qt6 的绕行（该路线作为备选保留在附录 A，已否决）。

决策 2：保留 Windows 分支，先本机验证再上 UOS。 即先在 Windows 用 Qt5 打通编译与冒烟测试， 确认降级本身没引入回归，再进 UOS 做平台后端适配。

决策 3（由决策 2 推导出的改造形态）：不删除 Qt6 支持，改为双版本兼容。 依据是 Qt 官方的 versionless 机制——Qt::Core 这类无版本前缀的目标在 Qt 5.15 与 Qt 6 中同时存在， 因此 Qt6::X → Qt::X 是一次双向生效的官方重命名，而非单向降级。 这带来两个直接收益：现有 Qt6 构建全程保持可用（可作二分对照基线，快速区分"降级引入的 bug"与"原有 bug"）， 且回滚成本极低。

降级工作量实测（当前 main 快照 grep 统计）：需改造 112 个 C++ 文件 + 882 行 CMake， 占非测试 C++ 文件总量的 8.6%。完整清单、兼容层代码、阶段计划与 Windows 环境前置 全部落在 docs-qt5-downgrade-plan.md。

决策 4：Linux 不做音频采集。 录屏在 UOS 上只录画面。理由不是"做不了"，而是代价与收益不成比例： PulseAudio / PipeWire 的客户端库全是 C 绑定，一旦引入，「平台后端只用纯 Rust」这条铁律就破了， 此后音频路径没有任何能在 Windows 上跑的门禁，只能靠真机反复试。而 snow-audio-recorder 在 Linux 上本来就已经是 UnsupportedBackend，保持"如实上报不可用"比给一个无法验证的实现更诚实。

⚠️ 新增前置阻塞：经实测，本机未安装 Qt / CMake / MSVC / Ninja / Rust / vcpkg，且仓库从未在本机构建过。 因此 Windows 验证前必须先完成环境 bootstrap（约 10–12 GB 下载、数小时），这是不可绕过的门槛。

1.3 构建与打包链路

  • Qt 供给：不使用 aqtinstall / vcpkg。由 scripts/qt-toolchain.json 单一真源锁定 6.12.0， cmake/SnowQt.cmake:29 执行 find_package(Qt6 <ver> EXACT REQUIRED)，版本不符即 FATAL_ERROR； SnowQt.cmake:39 注入 QT_DISABLE_DEPRECATED_UP_TO=0x060c00（Qt 6.5+ 专有宏）。 静态 Qt 由 scripts/build-static-qt.sh:143-160 从官方 tarball 自建，子模块仅 qtbase,qtsvg,qttools,qttranslations，并 -skip qtdeclarative。
  • 原生依赖：vcpkg manifest 模式，triplet 仅 {x64,arm64}-{windows,osx}-*（无 Linux triplet）。
  • Rust 集成：cmake/RustStaticLibrary.cmake 生成 cargo build --locked --package ... --target ... 自定义目标， 产物以 STATIC IMPORTED 挂到 CMake；snow_rust_ffi 单库聚合全部 C ABI。
  • 打包：Windows NSIS（根 CMakeLists.txt:426-485），macOS DragNDrop （cmake/SnowShotMacOSPackage.cmake）。无 Linux/deb/AppImage 配置。

三个必须写下来的判断（都是跨目标类型检查逼出来的）：

  1. bits_per_pixel 不在 visual 里。X11 的 Visualtype 只有 red_mask/green_mask/blue_mask； 每个深度的位宽与扫描线填充在 Setup.pixmap_formats。所以位宽按回复的 depth 去查 pixmap_formats，而不是从 visual 猜 32 —— 猜错就是整幅画面通道错位。 同理 GetImage 回复没有 bytes_per_line 字段：优先用回复长度反推（reply_stride）， 退路才是按 Format.scanline_pad 现算（scanline_bytes）。
  2. X11 像素没有 alpha。32bpp 的第 4 字节是填充（常见 0，也可能残留脏数据）， 解码一律写成不透明的 0xff —— 直接透传会得到带洞的截图。
  3. 根窗口读不到指针，也读不到别的窗口。指针由 X 合成在根窗口"之上"而非"之中"， 所以 create_target_capturer 保持默认（不提供原生采集器），光标交给会话的通用路径 （attach_cursor_to_frame → snow_cursor 的 X11 采样器）来画；窗口目标直接 BackendUnavailable —— 读别的窗口像素需要 Composite 重定向，这是硬缺口而非待办。

先修掉一个既有 Linux 硬阻塞：mouse/hook 的空实现里 start() 返回 Ok（一个永远不上报的观察器）， 只有 start_with_movement() 返回 Err。而 deferred.rs（Linux 目标下确实参与编译）走的正是后者 ⇒ Linux 上 InputRecorder::new 必然失败，录制根本起不来。空实现里"假装成功"的那一半正是问题所在， 两处都已换成真实现，not(any(windows, macos)) 门控随之改为 not(any(windows, macos, linux))。

四个必须写下来的判断（都是跨目标类型检查/交叉比对逼出来的）：

  1. 观测值必须说 Windows 虚拟键的空间。overlay 的 KeyObservation::event() 与 keyboard_overlay::modifier() 用硬编码的 0xa2/0xa3/0xa4/0xa5/0xa0/0xa1/0x5b/0x5c 索引 pressed 表，F1–F24 靠 0x70..=0x87、小键盘靠 0x60..=0x69 直接格式化。所以 Linux 后端不能透传 X11 键码，必须做 keysym→虚拟键映射（keys.rs）。macOS 走的是 0x100+原生键码 的第三空间，Linux 只在 映射不到时才退回 0x100+键码（见第 4 点）。
  2. keysym 描述的是"字符"，不是"键"。US 布局下同一个物理键给出 0x31(1) 与 0x21(!)， 而 Windows 虚拟键只有一个身份。故映射表建在字符上：! 与 1 归一、? 与 / 归一、;/: 归一， 与 Windows 的 VK_OEM_* 语义一致。钥匙帽显示什么则由 label(keysym) 决定 —— 它返回按下的那个字符 （!、Д），因此比"虚拟键→字符"反查更准（后者拿不到 Shift 层）。
  3. 不用原始事件的坐标，用 QueryPointer。RawMotion 的位置在设备 valuator 里，axisvalues 与 axisvalues_raw 哪个含加速值、相对设备按 FP1616 还是 FP3232 上报，没有真机就无法证伪， 而猜错的结果是"看起来合理但整体偏移"的光标轨迹 —— 最坏的一类错误。QueryPointer 在任何服务器/设备上 都无歧义。代价是每次采样一次往返，故运动采样上限 MOTION_SAMPLE_INTERVAL = 8ms（125 Hz）并在其间合并 ——消费端本来就只保留最新一条 movement，合并零损失。
  4. 观测器自己持有 pressed 表和键盘映射，于是按键事件零往返：shift/AltGr 层选择直接用本地 pressed 表算，不需要每次查询修饰键。映射在 MappingNotify 时重建（换布局后标签才不会继续描述旧布局）； 通道溢出后 generation 自增，并用 QueryKeymap 重建 pressed 表 —— 丢掉的批次里可能含 keyup， 不修就会让一个修饰键永久画在屏幕上。

其余刻意的取舍：

  • poll 而不是阻塞 wait_for_event：连接的 socket 归工作线程独占，Drop 没有任何办法打断阻塞读， 而录制收尾必须能随时结束观测器。改成 poll_for_event + 空闲 10ms 休眠（约 100 次/秒唤醒，比采集路径 自身的帧定时器低一个量级），代价是空闲时首事件最多在 socket 缓冲里等 10ms —— 抖动上限，远小于一帧。
  • alt_gr 恒为 false：X11 的 AltGr 是独立的键（映射到 0xa5，标签直接就是 AltGr）， 不是 Windows 那种"Ctrl+Alt 合成"的伪修饰。该标志的作用是隐藏伪装的 Ctrl 芯片，这里不存在。
  • 无 XInput2 时诚实失败：LinuxError::UnsupportedInputBackend（分类 InvalidConfig，不重试）， 而不是塞一个"返回空事件流"的实现 —— 后者会让录制器承诺一个永远不出现的键帽。
  • scan 字段在 Linux 上存 keysym：X11 没有硬件扫描码可报，而 keysym 正是 printable_label 需要的（scan 的语义本来就是每平台不同：Windows 是扫描码，macOS 是 keyboard_type）。 layout 字段在 Linux 上未使用（映射由观测器单点持有）。

9.4.5 P3 slice 4：键帽光栅化落地（2026-10-17）

五个必须写下来的判断：

  1. 不调 fontconfig。这是本片最重要的约束，与 x11rb 的选型同源：cargo check --target <linux-triple> 是本项目唯一能在 Windows 上验证 Linux 代码的门禁，一旦链接 C 库（fontconfig / FreeType），该门禁立刻需要 C 交叉工具链与 target 头文件，机制整个失效。所以族名解析改成 枚举字体文件 + 直接读 name 表（ttf-parser，纯 Rust），光栅化用 ab_glyph。代价是 fontconfig 的 alias / 替换规则（~/.config/fontconfig/fonts.conf）不生效，只做族名精确匹配。
  2. 只实现 rasterize，rasterize_glyph 沿用 trait 默认实现 —— 与 macOS 分支一致（macOS 也只实现 前者）。默认实现把 font_pixels / 32 当作 scale，playback.rs 的 TIMER_FONT_SIZE = 24 ⇒ scale 0.75。这个不能自己另算：playback 靠扫描返回位图的 alpha 通道来定位字形边界并推出基线 （glyph_top / digit_top），换一套度量就会让计时器数字的基线飘。
  3. 产物契约对齐 macOS 而不是 Windows。两边都能画成「带边框的圆角键帽」，但构造不同：macOS 是 border 铺满整图 + background 内缩 scale 像素（圆角 10 × scale），Windows 是矩形内缩 1.0 + 圆角 12 + 2px 描边。选 macOS 的形态，因为自绘一遍 fill 两遍更简单，且 Linux 与 macOS 同属 not(windows) 分支。尺寸公式与两边一致：ceil(fit(measured).0 × scale) by round(64 × scale)。
  4. 文本度量用 advance 累加，不做 kerning。主字体与 CJK 回退字体是两套坐标，跨字体的一对 kern 没有意义；同字体下对一两个字符的键帽图例影响不到 1px。macOS 的 CTLineGetTypographicBounds 本质也是 advance 宽度，所以这仍与 macOS 同源。
  5. 缺字回退的判据是 glyph_id(c) == 0。ab_glyph 对无轮廓的字符返回 .notdef（id 0）， 这正是 DirectWrite / CoreText 触发 cascade 的同一个条件。主字体缺失且没有回退字体时不报错， 退化成 .notdef 方框 —— 少一个汉字不该让整帧合成失败。但请求了一个未安装的族名要报错 （TextError::FontUnavailable）而不是换成别的字体：录出来的水印字体必须与应用程序其它地方一致。

其余刻意的取舍：

  • 圆角与边缘用 4×4 超采样覆盖率（16 样本/像素）而不是解析式 SDF：确定性、能写进断言、 没有浮点近似的争议。一个 64×144 的键帽约 15 万次 inside 测试，微秒量级，而 overlay 侧本来就有 256 项、32 MB 上限的键帽缓存。
  • 不做 hinting / 子像素定位：灰度抗锯齿与系统库同一档次，键帽是小字号大字重，差异不可见。
  • 默认族名候选表（Noto Sans CJK SC → Source Han Sans SC → WenQuanYi Micro Hei → Noto Sans → DejaVu Sans → Liberation Sans）只在请求未命名族名时使用；UOS / Deepin 默认 UI 字体是前两个。
  • 扫描跳过符号链接并限深 6 层，否则字体目录里一个指回父目录的链接会把一次枚举变成无边界遍历。 文件按路径排序后解析，保证同一台机器上字重平局的判定每次一样。

9.4.6 P3 slice 5：X11 窗口级拾取落地（2026-10-17）

slice 1–4 让 Linux「看上屏、看见手、画得出键帽」，这一片补的是指针指向谁： snow-ui-selector 在 Linux 上第一次有了 ElementRegionService，snow-ui-selector-c 随之恢复可编译。 这就是 9.4.2 里唯一一个 B 类门禁失败的根因，本片把它清零（46/60 → 48/60）。

范围是窗口级，不是控件级。 控件级要 AT-SPI2（另一个协议、另一条总线），本片没做， 也不假装做了 —— 见下面第 5 条判断。

层 位置 平台 内容
规则 snow-linux/src/window.rs 全平台 WindowKind / classify（_NET_WM_WINDOW_TYPE 折叠）/ selectable（可选中判据）/ DesktopWindows::hit_test（叠放序命中）。10 个单测在 Windows 上跑
对话 snow-linux/src/x11/window.rs linux desktop_windows_for：_NET_CLIENT_LIST → 逐窗口 GetWindowAttributes + _NET_WM_WINDOW_TYPE + GetGeometry + TranslateCoordinates → 根坐标 frame 矩形
接线 snow-ui-selector/src/linux.rs linux ElementRegionService：与 macOS provider 同形的 API（new / with_backend* / refresh* / release_cache / window_snapshot / from_snapshot / query），!Send/!Sync

五个必须写下来的判断：

  1. _NET_CLIENT_LIST 是自下而上，命中测试必须倒着找。这是本片最容易写错、且错了不会崩的地方： 正序遍历命中第一个，拿到的是最底层窗口 —— 表现为"选择器总指向后面那个应用"，看起来像 业务逻辑 bug 而不是遍历方向 bug。所以规则模块的文档注释和单测都把这条写在最前面 （the_topmost_window_wins 用两个完全重合的矩形来断言：叠放序相同则无法靠几何区分）。
  2. TranslateCoordinates 给的是内区原点，边框要自己补回来。X11 的 GetGeometry 里 width/height 是内区尺寸，border_width 单独给出；而用户看到的、他要截的那块是含边框的外框。 两者不一致时框会整体向内缩一圈，且窗口越有边框偏得越多。故 bounds = (dst − border, w + 2·border)。 translate_coordinates 的 same_screen == false 一律丢弃候选：那表示窗口在另一个 screen 上， 在本 screen 的根坐标里没有位置。
  3. 属性的三种状态必须分开：「读失败（窗口没了）」「属性不存在（type_ == NONE）」「存在但为空」。 - GetWindowAttributes / GetGeometry / TranslateCoordinates 失败 ⇒ 丢弃这一个候选，不让整次 枚举失败。桌面在任何时刻都有应用被关掉，一次瞬时竞态不该让选择器整体报错。 - _NET_CLIENT_LIST 属性不存在才回退到 QueryTree 遍历根窗口子窗口（reparenting WM 下的 frame 窗口）；存在但为空是窗口管理器在说"没有受管窗口"，此时回退会把 frame 当成窗口，是反的。 - _NET_WM_WINDOW_TYPE 不存在 ⇒ Normal。该属性是可选的，绝大多数应用根本不设； 若把"没写类型"当成"不可选中"，等于把几乎所有程序排除在外。
  4. _NET_WM_WINDOW_TYPE 与 override_redirect 两道过滤都要，因为它们描述的是不同的东西。 菜单/工具提示通常 override_redirect，于是根本不会出现在 _NET_CLIENT_LIST 里（受管窗口才进）； 但回退路径读的是根窗口子窗口，那时它们就在。反过来，dock/desktop 是受管窗口、会进列表。 单测 only_plain_application_windows_are_selectable 把七种"看似窗口但不可选"的形态列了一遍 （不可见 / override-redirect / InputOnly / 零面积 / 桌面 / 面板 / 瞬态），逐条断言被拒。
  5. HitTestMode::UiElement 与 Window 返回同一个窗口矩形 —— 这是有意的，且写进了模块文档。 没有控件级 provider 时，把窗口矩形当控件矩形返回会让调用方以为拿到了控件； 而返回"空元素集"会让 C 层以为无障碍可用但没结果（比编译失败更危险，与 9.4.2 原来的判断一致）。 所以只承诺窗口级，并在 query 的文档里写明"需要控件时应把本 provider 当窗口级退路"。

其余刻意的取舍：

  • 点落在窗口之间的空隙时报根窗口矩形，不返回空 path。空 path 在 C ABI 里是 path: None， 上层当作"这次没选中"；而 macOS provider 在同样情形返回显示器矩形。两者行为保持一致， 用户在裸桌面上点一下也能框到一块区域。
  • Point::window_id 优先：UI 线程已经用 QueryPointer 解析过命中窗口时，以它的答案收窄搜索范围。 两次遍历的时差可能让重叠窗口的结论不一致，让先解析的一方说了算，比让两边各自猜更稳。
  • 属性读取上限 MAX_PROPERTY_ITEMS = 1024：一次 hover 里读几千项的窗口列表不是任何真实桌面， 上限只是防止一个畸形属性把一次 hover 变成大分配。
  • release_cache 只清快照：X11 provider 不持有长生命周期的服务器对象，连接随快照一起丢掉； 这与 macOS provider 需要显式释放 AX 对象不同，因此"释放"在这里就是丢弃 WindowSnapshot。

9.4.7 P3 slice 6：MIT-SHM 零拷贝采集（2026-10-17）

slice 2 的 X11 采集能出画面，但每帧的像素要穿过整条连接：服务端分配回复、拷进去，客户端再拷出来。 1920×1080 一帧 ≈ 8 MB，三份拷贝，按录制帧率重复。本片把这条路换成 MIT-SHM： 服务端直接写进双方共享的内存，回复里只剩深度与字节数。

层 位置 平台 内容
尺寸规则 snow-linux/src/capture.rs::shm_segment_size 全平台 按服务端的 scanline_pad 规则算段大小，溢出/退化返回 None。4 个单测在 Windows 上跑
对话 snow-linux/src/x11/shm.rs linux Segment（CreateSegment 取 fd + mmap）、prepare_shm（分配/按需扩大）、read_shm_image（ShmGetImage + 用回复的 size 反推 stride）
接线 snow-linux/src/x11.rs::capture_image linux 先 prepare_shm（&mut）再 read_image（&self）；后者优先读共享段，不可用则 GetImage

为什么这仍然是"纯 Rust"且不缩门禁：CreateSegment（MIT-SHM 1.2）由服务端分配段并把 fd 传回来， 客户端只用 memmap2 映射（它本身也不含 C 源码）。换成经典的 SysV shmget + Attach 也能做， 但那要直接调 libc，且段的生命周期要自己用 shmctl(IPC_RMID) 管；CreateSegment 的段随连接消失。

五个判断：

  1. ShmGetImage 没有回复数据，所以必须先分配再知道大小。这是与 GetImage 最根本的差别： 后者可以「读回复 → 从长度反推 stride」，前者必须在发请求前就算出字节数， 算小了服务端就写越界。故用 shm_segment_size（与服务端同一套 padding 规则）估算， 再用回复里的 size 反推真实 stride（复用 slice 2 的 reply_stride）——不信任自己的估算。
  2. 失败是连接级属性，不是瞬时故障。远程 TCP 显示、无 MIT-SHM 的服务器、拒绝映射 fd 的沙箱， 这三种情况都不会因为下一帧而改变。所以第一次失败就把会话标成 Unavailable 并按 GetImage 走到底； 若每帧重试，等于每帧多一次往返去确认同一件事。
  3. 越界一律不读。服务端已经在回复到达前写完了，所以 size > 段长 时数据可能已经越界； 该帧直接交给 GetImage（它带回长度可校验）。另外 mmap 按页映射，小幅越界通常落在同一页里 不会崩 —— 但这是"没崩"，不是"正确"，不能拿来当保证。
  4. 准备与读取必须拆成两个函数。分配需要 &mut self，而读取要把映射里的切片借出去； 一个方法同时做两件事，就会出现「一条路径返回自身借用、另一条路径继续用自身」—— 可变借用的生命周期被返回类型钉死到整个函数体，编译器直接拒绝。这个拆分是编译器逼出来的， 不是风格选择。
  5. capture_access_active 仍为 false：共享段不是"采集访问句柄"，释放它并不会让别的程序 重新获得采集能力。语义没变，就没有理由跟着改。

9.4.8 P4 slice 1：Rust↔C++ 平台桥 + 物理光标（2026-10-17）

P4 的第一个问题不是"写什么"，而是写在哪里才能被验证。C++ 侧在这个仓库里一行都没被编译过 （本机没有 Linux C++ 交叉工具链，也没有 Qt5 的 Linux 头），所以如果直接把 Win32 调用逐条翻译成 Xlib 调用，产出的是一批只能靠眼睛读的代码。本片的取舍是：把逻辑压到纯 Rust 里（可跨目标类型检查 + 可在 Windows 上跑单测），C++ 只剩转发，并先用一个最小能力把桥建立起来，后续 P4 各项复用同一座桥。

接线 snow_shot/src/platform/physicalcursor.cpp linux #elif defined(Q_OS_LINUX) 分支，形状与 macOS 分支同构；CMake 用遍历把所有编译该文件的 target 都链上 snow_shot_linux_platform

为什么非要另开一个 archive（实测依据，不是偏好）：把这段代码塞进 snow_rust_ffi 是更"自然"的做法， 但本机实测那个 archive 的 Linux 目标 cargo check 在 zstd-sys 就断了（A 类，需 C 交叉编译器）， 永远走不到我们的代码。也就是说：塞进去 = 写了但没有门禁。新 archive 只依赖纯 Rust 的 snow-linux， 每次 bash scripts/linux-cross-check.sh 都会真的编译它。代价是 C++ 侧多链一个静态库。

六个判断：

  1. 句柄不持有连接。Qt 在热路径上构造临时 PhysicalCursor（globalcanvascontroller.cpp:68 与 :387 都是 platform::PhysicalCursor().logicalPosition()），若一实例一条连接，就是每次鼠标移动做一次 X11 握手。所以连接放进 OnceLock<Option<Mutex<X11Session>>>，句柄只是一个能力令牌 + 以后挂 per-caller 状态的地方；create 返回 NULL 就等于"这个会话不支持"。
  2. 第一次尝试决定终身。会话打不开要么是永久的（纯 Wayland 无 XWayland），要么是暂时的 （合成器还没起来）。每次调用重试等于每次花一次握手去确认同一个答案；而应用本身没有 X 就跑不起来， 所以这个 latch 的代价可以接受 —— 但必须写在文档里，不能让人以为是随机失败。
  3. WarpPointer 没有回复，所以必须显式 flush。否则请求躺在外发缓冲里，直到下一次需要回复的 请求顺手把它冲出去，光标会在一个不可预测的时刻跳。这类 bug 不报错、不复现，只是"有时候不灵"。
  4. 越界要拒绝，不要 clamp、更不要 as 转。root 坐标是 i16，而 C ABI 收的是 int32_t； as i16 会把 32768 变成 -32768，把光标送到对面角落。RootPosition::new 返回 Option， C 侧拿 0（失败）。同样地，也不 clamp 到屏幕边缘 —— 那会把调用方的 bug 藏在一个"只是位置不对"的 现象后面。
  5. same_screen == false 必须当成"没有位置"。QueryPointer 的坐标是相对持有指针的那个 root； 本后端只连一个 screen，把别的 root 的坐标当本 root 的读出来，结果是光标跳到左上角，而不是读取失败。
  6. 不提供 readLogicalPosition，也不合成鼠标事件。X11 的 root 坐标是设备像素，而 logical 坐标 依赖屏幕缩放 —— 那是 QCursor::pos() 已经算过的事，在这里再算一遍是"用更少信息给出第二个答案"。 反过来，X11 的 warp 对服务器而言是真实的 motion 事件（与 macOS 的 CGWarpMouseCursorPosition 相反）， 所以 generatesMouseMoveEvents 保持 true，不需要 QWindowSystemInterface 合成。

两个附带判断：

  • C++ 分支要先看 QGuiApplication::platformName() == "xcb"。Wayland 会话下即使有 XWayland， Qt 的 platform 仍是 wayland；此时 XQueryPointer 读的是 XWayland 自己那份指针副本， 指针离开 X 窗口后就不再跟随。那是一个"过期的位置"，比"不支持"更糟。
  • CMake 的链接不能只写一处，也要防匹配器静默失效。静态库可以留 undefined 符号，最终可执行文件不行； 而仓库里多个测试 target 会各自重编 physicalcursor.cpp。所以沿用本文件中已有的 canvas_status_readout 遍历写法，但加一条配置期自检：一个 target 都没匹配到就 FATAL_ERROR。 否则匹配器写错的表现会是链接期的 undefined symbol，出现在离原因很远的日志里。

附录 A：AppImage 打包路线与「保留 Qt6」可行性

A.1 直接回答

技术上可行，但约束只是换了地方。

AppImage 把应用连同 Qt 一起打进单个可执行文件，运行时由 AppRun 设置 LD_LIBRARY_PATH / QT_PLUGIN_PATH，因此不依赖宿主系统的 Qt 版本——这也意味着不再需要把代码降级到 Qt5： QKeyCombination、QNativeInterface，乃至 snow_image_viewer 的 QRhi 都可以原样保留。

但它同时引入一个比 Qt5 更硬的约束：glibc 基线。AppImage 无法打包 glibc （glibc 不可重定位，官方亦明确不支持声明最低 glibc 要求），宿主的 glibc 必须 ≥ 构建基线。

结论：能否在 UOS 上保留 Qt6，不取决于 AppImage，而取决于「目标机 glibc 版本」与「本工程 Qt 6.12 的构建基线」的相对关系。

A.2 AppImage 能打包什么 / 不能打包什么

能打进 AppImage 必须由宿主提供（打不进）
Qt6 全套库 + 平台插件（libqxcb.so / libqwayland-*.so） glibc（不可重定位）
libstdc++ / libgcc_s GPU 驱动：libGL / libEGL / libdrm（必须用宿主的）
FFmpeg / OpenCV / onnxruntime / 图像编解码库 xdg-desktop-portal（Wayland 采集入口）
自研 Rust 静态库、.qm 翻译、字体 PipeWire / PulseAudio 守护进程
应用本体与资源 D-Bus session bus、AT-SPI、polkit、CUPS、X11/Wayland 合成器

⚠️ 关键推论：AppImage 解决不了本方案的主要工作量（L2 平台后端）。 屏幕采集（portal + PipeWire）、音频、全局输入钩子、UI 元素拾取全部依赖宿主服务与内核接口， 打包行为对此毫无帮助——第 8 章的 P3 / P4 工作量一项都省不掉。

A.6 AppImage 落地注意事项（与本工程相关）

  1. FUSE2 依赖：AppImage 需要 libfuse2（不是 fuse3）。UOS 可能未预装， 需 sudo apt install libfuse2；否则用 --appimage-extract-and-run 兜底（体验下降，需解压约 1GB）。
  2. 切勿打包 libGL / libEGL / libdrm：linuxdeploy 默认排除这些是正确行为—— 打包会导致 GPU 驱动失配、渲染异常。
  3. Qt 平台插件链必须完整：platforms/libqxcb.so 依赖一长串 libxcb-*、libxkbcommon 与 xcbglintegrations/*，建议用 linuxdeploy-plugin-qt 自动收集，并逐个 ldd 核对。
  4. Wayland 会话：需同时打包 libqwayland-*.so 与 libwayland-client； 但采集仍须走宿主 portal，打包无济于事。
  5. 桌面集成缺口：AppImage 不会自动创建菜单项、托盘、开机自启。本工程的"开机自启"会写 ~/.config/autostart/*.desktop 并指向 AppImage 绝对路径——用户一旦移动文件即失效， 需在 UI 中显式提示（避免"设了自启却没生效"的误导）。
  6. 单实例：QLocalServer（snow_shot/src/app/singleinstancecoordinator.cpp）在 AppImage 下正常，无需改动。
  7. 提权：pkexec 走宿主 polkit，正常工作。
  8. 更新：AppImage 不受系统包管理器管理，需自建更新通道（AppImageUpdate / zsync 或应用内自更新）。
  9. arm64：需 aarch64 版 appimagetool 与 arm64 libfuse2；同样准备 --appimage-extract-and-run 兜底。
  10. 静态 Qt 变体：本工程已支持 SNOW_APPS_QT_STATIC。snow_shot 为 GPL-3.0， 静态链接 Qt 在许可上成立，且能规避插件路径问题——可作为路线 B 的简化形态。

A.7 合规提醒（重要）

在信创采购 / 等保 / 国产化适配认证场景中，AppImage 通常不被认可： 它不在信创软件目录内，且认证审查一般要求使用系统提供的基础库而非自带副本。 若本项目的 Qt5 约束来自认证要求，则 AppImage 打包 Qt6 极可能通不过评审， 必须维持 Qt5 路线（折中方案：采用 deepin-shared-libs 提供的 Qt 5.15.10）。
